# optimized-standard-access-pairing — 优化/标准访问必须配对与"丢数据"四步因果链

## R — Reading（原文）

> "请确保以下情况：如果函数块的设置是'Optimized block access'(优化的块访问)，则该函数块的背景数据块的设置也应该是'Optimized block access'(优化的块访问)。……如果没有兼容的块访问类型，那么在函数块执行期间从人机界面对该函数块的 IN/OUT 参数值所做的更改可能会丢失。"（p159，说明框）

> "1. 用户程序准备调用该函数时，系统必须制作该结构的一个'副本'…… 2. 用户程序采用该结构的该'副本'的引用调用该函数。 3. 该函数运行期间出现了一个中断组织块，且该中断组织块更改了原结构中的某个值。 4. 该函数运行完毕。……系统将该值以原来的格式复制回原结构。"（p161）

> "采用制作结构副本的方式进行格式转换的后果：该中断组织块改写过的数据将被丢失。使用 HMI 写入值时，情况也是如此。"（p161）

## I — Interpretation（自述）

S7-1200 的每个程序块（FB/DB）都有一个"优化块访问"开关，新块**默认勾选**。规则是：FB 与它的背景 DB 必须同型——FB 优化则背景 DB 也要优化；FB 标准则背景 DB 也要标准。传 STRUCT 类 IN/OUT 参数时，系统还会检查**实参所在全局 DB** 与 FB 的设置：两者一致 → 传引用，无副本，无风险；**两者失配** → 系统必须先复制一份 STRUCT 并转格式，再以副本调用 FB。失配的代价在特定时序下爆炸：FB 执行期间若中断 OB 或 HMI 改了**原结构**，FB 结束时系统会把（调用开始时复制的）副本按原格式写回——**把中断/HMI 的写入覆盖掉**。整个链条**没有任何报错**：CPU 不停机、无诊断缓冲区条目、无错误码，表现为"偶发丢数据"，是全手册唯一写全因果链的静默失败。修复两条路（p161）：最好 = 统一优化设置（消掉副本）；次选 = 让中断 OB/HMI 改另一个变量，再在程序特定位置复制进结构。首要怀疑对象：从旧项目复制来的、或手工改过属性的 DB——因为新建 DB 默认就是优化访问。

## A1 — Application Example（标注演练：验证记录 T1 演练，纸面可复算）

**【合成演练（T1 纸面推演，逐条对应 p161 原文编号），原书未提供成例】**
场景：FB 500 "MotorCtrl"（优化）有 IN/OUT 参数 `stStatus : Struct {Speed : Real; Run : Bool}`；实参在全局 DB 100 "gMotor"（**标准访问**，从旧项目复制而来）；OB 200（10 ms 循环中断）写 `gMotor.Run := TRUE`；HMI 画面写 `gMotor.Speed := 1500.0`。
1. 列清单：DB 100 = 标准访问；FB 500 = 优化；背景 DB 501 必须与 FB 一致（p159）→ **第一处失配**（全局 DB vs FB）。
2. 命中 p161 四步：调用时系统复制 STRUCT → 以副本引用调用 → OB 200/HMI 改**原结构** → FB 结束副本回写，**覆盖 OB 200 与 HMI 的写入**。
3. 可观察证据（唯一）：OB 200 每周期写 TRUE，FB 结束后 `gMotor.Run` 回 FALSE；**无任何诊断/报警/返回码**——演练不得补造报错。
4. 修复（二选一，p161）：A. 把 DB 100 与 FB 500（连带背景 DB 501）优化设置改一致；B. OB 200/HMI 改写独立变量，由 OB 1 在固定位置复制进结构。
5. 复算边界：手册未给"丢一次的时序概率"，本演练只证"存在丢失时序"，不预测频率。

## A2 — Future Trigger ★

**触发场景**：
1. "HMI 写进去的值过一会儿又变回去了 / HMI setpoints are lost randomly"——偶发性是最强信号。
2. "中断 OB 里改的值主程序总是读不到/被改回去。"
3. 把旧项目块复制进新项目后开始出现丢数据："移植后 HMI 写入不生效了。"
4. 评审程序结构时问："FB 和背景 DB 的优化设置要不要一致 / optimized vs standard block access?"
5. 背景数据块不能按绝对地址 PEEK/POKE 访问，追查原因时发现访问类型问题。

**语言信号**：优化块访问 / optimized block access、标准访问 / standard access、HMI 写入丢失 / HMI writes lost、值被改回 / value overwritten、背景 DB / instance DB、IN/OUT、STRUCT、偶发 / intermittent。

**与相邻 skill 的区分**（初稿）：症状是"**写入被回滚/丢失**"且与 FB 调用相关 → 本卡；症状是"**跨 OB 读到半更新/不一致的数据**"（撕裂读，需 DIS_AIRT/访问一致性问题）→ DIS_AIRT router 卡（两卡互写近邻负例）；症状是"通信链路本身断/连不上" → connection-budget 卡；读数是异常值 32767 → 32767 卡。

## E — Execution（可执行步骤）

**输入契约**（缺则先问）：①被怀疑丢数据的变量所在的 DB/FB 清单；②该变量是否经 IN/OUT 结构参数或被中断 OB/HMI 直接写；③块属性中"优化块访问"勾选态（DB、FB、背景 DB 三者逐个读）；④TIA Portal 是否可批量导出优化标志（手册未给批量工具——没有则按逐块人工核对执行，不静默跳过）。

**步骤**：
1. **Step 1 三点清单**：对每个嫌疑链路读三个勾选态——全局 DB、FB、其背景 DB（项目树 → 右键 → 属性 → 特性）。✅ 完成标准：每个块都有"优化/标准"记录，无一遗漏（最小检查面 = 三点，两两一致）。
2. **Step 2 配对判定**（判停点）：三点全部一致 → 传引用、无副本，本卡到此结束（若仍丢数据 → 转相邻卡排查）；任一失配 → 命中四步因果链，进入 Step 3。✅ 完成标准：明确指出哪两点失配。
3. **Step 3 修复二选一**（p161 原文两条解法）：A. 统一优化设置（注意背景 DB 随 FB 走）→ 需重新编译下载；B. 隔离写入——中断 OB/HMI 改独立变量，OB 1 在固定位置复制进 STRUCT。✅ 完成标准：选定路线并说明代价（A 动块属性需下载；B 需加复制代码）。
4. **Step 4 验证**：恢复后让中断 OB 写 TRUE、FB 持续运行数周期，确认写入保持；HMI 写值同法。✅ 完成标准：写入值跨 FB 调用边界保持不变。

**输出契约**：一张"块访问类型清单表"（列：块名｜类型 DB/FB/背景DB｜优化勾选态｜与邻居是否一致）+ 失配结论 + 修复动作 + 复验结果。**约定**：手册未提供失配时的任何错误码——输出表不得虚构"报错记录"栏；验证手段只有在线监视值。

## B — Boundary（边界与失败模式）

- **反场景**：数据"读到一半更新"的撕裂读/跨 OB 一致性 → DIS_AIRT router 卡；通信断线/HMI 掉线 → connection-budget 卡；值是错的而不是丢的 → 32767 卡或 analog-scaling 卡；STOP 类严重故障 → router。
- **手册警告的失败模式**：本卡全部三条引用（p159 后果句、p161 四步链、"数据将被丢失"）的共性 = **零报错静默失败**；手册未给任何诊断手段，验证记录实证"无错误码、无诊断缓冲区条目"。
- **易漏点**：①只查 FB↔背景 DB 会漏掉**全局 DB↔FB** 这一处失配（四步链的实参在全局 DB 时同样中招）；②新建 DB 默认优化，从旧项目复制/手工改过的 DB 是首要怀疑对象；③PEEK/POKE 等绝对地址访问**只能用标准 DB**（优化块无固定地址，p158 定义推论）——两方向各有约束，别把"都改优化"当万能解。
- **阶段 0 批判盲点**：手册未提供批量识别优化标志的工具或步骤（验证记录确认的真实缺口），大型项目逐块核对成本高——本卡如实标注该缺口，不补造工具步骤。
- **相邻易混淆**：与 DIS_AIRT 卡同在"偶发数据异常"域；分流词 = "写丢了/被回滚"（本卡）vs "读到新旧夹杂"（DIS_AIRT）。
