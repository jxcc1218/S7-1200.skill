# 能力卡：扫描周期监视 STOP 阶梯（二次超时即 STOP、OB 80 不豁免、删除 OB 80 更危险）

## R（原文引用）
> "如果时间错误中断 OB 从未下载，则会忽略第一个超时条件并且 CPU 保持在 RUN 模式下。如果在同一程序扫描中第二次发生最大扫描时间超时（2 倍的最大循环时间值），则触发错误会导致切换到 STOP 模式。"（p248）
> "如果之前已下载时间错误中断 OB，但后来已将其删除，则如果发生时间错误事件，CPU 会切换到 STOP 模式，因为 CPU 找不到时间错误 OB。"（p76）
> ——《S7-1200 系统手册》V4.7，6.1.4 监视和组态循环时间

## I（自述）
最大扫描周期监视（默认 150 ms，1–6000 ms，始终启用）的 STOP 阶梯有四级：①首次超时——有 OB80 就执行 OB80；没有 OB80 则忽略首次超时、保持 RUN（只写诊断缓冲区）；②同一扫描周期第二次超时（即达到 2×最大值）→ 直接 STOP，**组态了 OB80 也不豁免**；③曾下载过 OB80 后来删除 → 任何时间错误直接 STOP（找不到 OB）；④缓解手段：组态"超时保持 RUN" + RE_TRIGR 指令复位周期计时（当前循环耗时 <10×最大值时才有效，ENO=TRUE，p76/p248）。

## A1（合成演练，含可复算数值）
原书未提供完整数值算例。合成演练：最大周期=150 ms。场景 A（无 OB80）：循环 1 耗 160 ms → 忽略+缓冲条目；循环 2 耗 310 ms（>150 已是同扫描第二次超时）→ STOP。场景 B（有 OB80）：160 ms → 执行 OB80；310 ms 的二次超时 → 仍 STOP。场景 C：下载过 OB80 后删除，第一次 160 ms → 直接 STOP。

## A2（未来触发）
- 场景："CPU 偶发转 STOP"排查的第一站；问"超时为什么没报 OB80/为什么直接停"；评估删除 OB80 的后果。
- 语言信号：中"扫描周期超时／最大循环时间／OB80／CPU 转 STOP"；英"cycle time exceeded / OB80 / CPU goes STOP on timeout"。
- 相邻区分：**诊断缓冲区怎么读/时间轴** → diag-buffer-interpretation（晋级决策表注明两卡共触发，本卡管"判据阶梯"，那卡管"读缓冲与分流"）；某条指令为什么慢（通信负载/循环中断组态）→ router。

## E（执行步骤）
1. 输入契约：诊断缓冲区时间轴（超时条目+模式切换条目）+ CPU 周期组态值。
2. 定位超时条目，判断是否存在 OB80（历史下载记录）。
3. 按阶梯判定根因：单次超时被忽略？二次超时 STOP？OB80 被删？
4. 处置（按优先级）：a) 压缩程序/挪通信负载（通信负载百分比可调，p77）；b) 调大最大周期（≤6000 ms）并复测；c) 确需容忍 → 组态保持 RUN + RE_TRIGR 门控。
5. 禁止动作：不要用"删除 OB80"来解决超时（升级为直接 STOP）。
6. 完成标准：复测若干天无新增超时条目且 CPU 保持 RUN；自查：每次修改后在缓冲区确认超时条目频率变化。

## B（边界）
- 反场景：故障模式重启（三灯持续闪烁，p948）是固件级严重错误，不是周期超时；硬件故障诊断 → router。
- 手册口径：RE_TRIGR 生效条件"当前程序循环执行耗费的时间小于所组态最大扫描周期时间的十倍"（p76）——已接近 10 倍的循环它救不了。
- 矛盾/勘误：p74 footnote 3 与 p75/p248 表述一致（同一扫描周期第二次超时→STOP），无冲突。
- 外链缺口：CPU 过载行为与事件排队细节 → STEP 7 Information System（p74 指引）。
