# connection-budget — 连接资源核算：第 N 台设备为什么连不上

## R — Reading（原文）

> "S7-1200 CPU 具有 34 个动态资源。"（p478）

> "由于动态连接是共享资源，因此无法同时实现所有连接的最大数量。"（p478，表脚注 1）

> "在添加 CM/CP 模块时，S7-1200 通信连接的总数不增加。"（p478，说明）

> "根据拥有的 HMI 类型或型号以及使用的 HMI 功能，每个 HMI 实际可能使用其可用连接资源中的一个、两个或三个。……但是，要始终确保至少有四个 HMI。"（p478）

> "对于每个 HMI，CPU 支持 400 个变量和最多 40 个 HMI 订阅。"（p579）

## I — Interpretation（自述）

S7-1200 的"能同时接几台 HMI/几个 PG/几条 S7 连接"不是查单一数字，而是一张**两层预算表**：第一层是**预留资源**（保证资源）——每类连接保底的数量，如 HMI 保底 12、PG 保底 4、S7 通信保底 8、OUC 保底 8、Web 保底 2、OPC UA 保底 0；第二层是 **34 个动态资源**（自由资源）——任何类型用超预留后从这里扣，没有任何预留的类型（OPC UA、其它通信）也从这里出。**34 是硬总数**：加 CM/CP 模块**不增加**它；每类连接的"最大值"列（HMI 18、S7 14、OUC 14、Web 30、OPC UA 10）加起来远超 34，所以脚注明说**不可能同时实现各类最大值**。HMI 的单价是 1–3 个资源/台（读取/写入/报警诊断三个功能各占其一），随型号与用法浮动。因此"第 13 台 HMI 连不上"这类问题的解法是：列连接清单 → 按类核算占用 → 与预留+34 对账 → 给出"砍谁/减订阅/加什么不行"的结论。另外还有一层**单机口径**：每台 HMI 上限 400 变量 + 40 订阅，与连接数无关，是第二个独立闸门。

## A1 — Application Example（书中算例 + 标注演练）

**书中算例（p479 表）**：5 台 HMI 的占用示例——HMI 1/2/3 各用 2 个资源，HMI 4/5 各用 3 个，合计 **12**（"这仅仅是个示例，实际数量根据 HMI 类型和版本而不同"）。配套规则：至少保 4 台 HMI（12 预留 ÷ 3 功能 = 4）。

**【合成演练，按 p478 规则复算】** 某站：4 PG（调试）+ 12 台轻量 HMI（每台只读，各 1 资源）+ 4 条 OUC（TSEND_C 各 1）+ OPC UA 服务器 10 会话 + Web 2。问动态池还剩多少？
1. 预留侧对账：PG 4（≤4 ✓）、HMI 12（=12 ✓）、OUC 4（≤8 ✓）、Web 2（=2 ✓）、OPC UA 0（预留 0）→ 全部落在预留内。
2. 动态池核算：OPC UA 10 个会话全吃动态（预留 0）→ 动态占用 10，**剩 24**。
3. 扩容问：再加 12 台 HMI？→ HMI 共 24 台，超预留 12 台各吃 1 动态 → 动态占用 22，剩 12，**可行**（p477 明确"可组态'可用自由连接'以增加任意类别的连接数"）。
4. 反例对照：若同时想把 OPC UA 开到 20 → 越过该类最大值 10，**不可行**；幻想"各类都取最大值"4+18+14+14+30+10=90 > 34，被脚注 1 否定。
5. 复算口径：所有数字取自 p478 表；"其它通信 0/–"不参与最大值推算（手册给"-"）。

## A2 — Future Trigger ★

**触发场景**：
1. "这台 CPU 最多能接几台 HMI / how many HMIs can I connect?"（组态期规划）
2. "第 N 台 HMI 突然连不上了，前 N−1 台都正常"——现场加设备后偶发连不上，根因排查第一入口。
3. "加了 CP/CM 卡连接数会不会变多 / does adding a CP increase connections?"（答案：总数 34 不变）
4. 规划 OPC UA 会话数、Web 浏览器并发数、TSEND_C 连接条数时问"还剩多少连接资源"。
5. Modbus TCP 客户端/服务器混合部署时问并发连接上限（受 OUC 上限约束，p918）。

**语言信号**：连接资源 / connection resources、34 个连接 / dynamic resources、最多几台 HMI / max HMI connections、预留/动态 / reserved/dynamic、加 CP 能不能扩 / CM CP connections、连不上 / cannot connect（批量场景）。

**与相邻 skill 的区分**（初稿）：**资源够不够**（数量型问题，本卡）vs **端口/防火墙通不通**（可达型问题）→ port-state router 卡——分流判据：把连接数减回可工作数量后立即恢复 = 资源问题；数量不变而个别服务不通 = 端口/防火墙。知道 IP 但某服务不通 → port-state；彻底不知道 IP → emergency-ip-recovery 卡。单台 HMI 变量/订阅超 400/40 → 本卡 E 段第二闸门。

## E — Execution（可执行步骤）

**输入契约**（缺则先问）：①CPU 型号（所有 S7-1200 动态池同 34；预留行同表）；②完整连接清单——每类（PG/HMI/S7/OUC/Web/OPC UA/其它/Modbus TCP 归 OUC 口径）的**台数或条数**；③每台 HMI 的功能面（只读/读写/带报警诊断——决定 1/2/3 单价）；④CPU 固件与项目组态（连接分配按组态生效）。

**步骤**：
1. **Step 1 建清单**：按 p478 七行类型列表填"类｜数量｜单价（资源/台或条）"。✅ 完成标准：清单行数 = 实际使用的连接类型数，无凭空类别。
2. **Step 2 预留层对账**：每类算占用 = min(数量, 预留数)；**同类的超出部分转入动态层**；预留为 0 的类（OPC UA/其它）全额转动态。✅ 完成标准：每类给出"预留内占用/动态占用"两段。
3. **Step 3 动态层总账**：动态占用合计 ≤ 34 判可行；> 34 判超限。**双闸门复查**：每台 HMI 变量数 ≤ 400 且订阅 ≤ 40（p579）。✅ 完成标准：一个总数 + 一句"34 是否够"。
4. **Step 4 处置结论**（判停分支）：超限 → 可选动作按优先级：削减 HMI 功能面（3→1 资源/台）、降 OPC UA 会话数、合并 OUC 连接；**"加 CP/CM 扩容"不可选**（p478 明文总数不增）。若"减回即恢复"→ 资源结论成立并出核算表；若数量未超仍连不上 → 移交 port-state router 卡。

**输出契约**：连接预算表（字段：类型｜预留｜最大值｜本站数量｜单价｜预留内占用｜动态占用），合计行动态总数，结论行（可行/超限 N 个）+ 处置建议。**约定与容差**：HMI 单价 1/2/3 由功能面决定，清单里必须写明判据；"其它通信"最大值列为"–"，**不得**推导任何上限；Web 最大 30 是上限非保证（同时可支持的浏览器数取决于动态资源余量）。

## B — Boundary（边界与失败模式）

- **反场景**：IP 不知道/被锁在门外 → emergency-ip-recovery 卡；端口默认态/防火墙黑名单（20/80/102/5001/34962–34964 等两套口径，p565 vs p577，澄清清单 A4 未定论）→ port-state router 卡；单连接协议参数（TSAP/端口/连接 ID）配错 → router；Web 登录被锁 30 分钟 → router。
- **手册警告的失败模式**：①"无法同时实现所有连接的最大数量"——按最大值列做容量规划必然翻车；②加 CM/CP 不增总数——最常见的错误扩容假设；③OPC UA 预留为 0，"确保应用程序有足够的可用连接"（p478），开满 10 会话前不查动态池余量 = 静默挤掉其它连接；④HMI 数量够但**每台**超 400 变量/40 订阅，表现为该台读不到数据（与连接数是两个独立闸门）。
- **口径缺口（如实标注）**：CPU 规格表中连接资源的型号级表述（预留合计/最大总数）在验证阶段为 needs_review（C-969，未回原文对齐 p999/p1010）；本卡全部数字取自 p477–479 正文口径，不做型号级外推。Modbus 并发归入 OUC 上限的口径以 p918 正文为据。
- **阶段 0 批判盲点**：手册给的是"类"级表格，没有"台"级单价表（HMI 单价随型号/版本浮动，p479 自称"仅仅是个示例"）——核算表里的单价列必须写判定依据，禁止拍脑袋填 1。
- **相邻易混淆**：与 port-state 同在"连不上"域；数量型/可达型的分流在阶段 4 实测。
