# 能力卡：MB_CLIENT 请求期冻结输入（改输入→无法确定活动实例→失序）

## R（原文引用）
> "Modbus 客户端启动 Modbus 操作后，将在内部保存所有输入状态，然后在每次后续调用时进行比较。比较用于确定此特定调用是否是活动客户端请求的发起者。……在主动处理 MB_CLIENT 操作期间应不改变输入，这一点很重要。若不遵循此规则，则 MB_CLIENT 无法确定活动实例。"
> ——《S7-1200 系统手册》V4.7，14.5 Modbus 通信，p819

## I（自述）
MB_CLIENT 的活动实例判定机制：请求启动时把全部输入快照保存，之后每次调用都比对新输入——只有"输入从未变过"的那个调用才被认定为活动请求的发起者。如果请求进行中（DONE/ERROR 返回前）改了任何输入（REQ、MB_MODE、MB_DATA_ADDR、MB_DATA_LEN、MB_DATA_PTR 等），指令就无法把新状态匹配到活动实例 → 请求失序甚至挂住。这是静默失败：不报错，表现为"请求没发出去"或时序错乱。正确姿势：用 DONE（完成时一个周期为 TRUE）做定时门，完成后再改参数、再触发下一个请求。

## A1（合成演练，含可复算数值）
原书未提供本条算例。合成演练：REQ 上升沿发起读 40021 起 100 字（RCV_TIMEOUT 默认 2.0 s），发起后 0.5 s 程序把 MB_DATA_LEN 从 100 改为 50 → 活动实例无法确认，后续 REQ=1 不会再发新传送（p819："不会进行后续 Modbus 传送"）。整改：等 DONE=TRUE（一个周期）→ 改 LEN=50 → 再 REQ。每个 MB_CLIENT 调用用唯一背景 DB（p821–822 多连接规则）。

## A2（未来触发）
- 场景：Modbus TCP 客户端偶发不发请求/多请求调度失序；轮询程序里动态改地址后"卡住"。
- 语言信号：中"MB_CLIENT 请求被忽略／REQ 不响应／请求卡死失序"；英"MB_CLIENT request not sent / active instance / REQ edge ignored"。
- 相邻区分：服务器端安全边界（默认全开 I/Q）→ mb-server-default-open-ports；超时值与 80C8 口径 → mb-client-timeout-variables；Modbus RTU 主站（Modbus_Master 同样在请求期间捕获输入、同规则，p878）→ router。

## E（执行步骤）
1. 输入契约：触发时序（REQ 在哪个 OB、何时变沿）+ 请求参数变更点。
2. 排查所有"请求完成前改输入"的路径：程序赋值、HMI 写连接参数、启动逻辑覆盖。
3. 整改：以 DONE（或 ERROR）=TRUE 为门，先完成再改参再 REQ；两请求间必须观察到一次 DONE/ERROR。
4. 多实例：每连接唯一背景 DB + 唯一连接 ID（p822）。
5. 静默失败自查：现象=请求没发且 STATUS 无错 → 画 REQ/输入/DONE 时序，找请求窗口内的输入变化。
6. 完成标准：请求按序完成，DONE 门控逻辑评审通过。

## B（边界）
- 反场景：STATUS=80C8 超时（服务器无响应）→ mb-client-timeout-variables；服务器侧问题 → mb-server 卡。
- 手册口径：输入一致性约束也适用于"使用公用背景数据块执行多个 MB_CLIENT 调用"的场景（p819）。
- 矛盾/勘误：C-917（超时静态变量口径）已并入本域；无逐字矛盾。
- 外链缺口：第三方 Modbus TCP 服务器要求特殊端口号/UNIT_ID 范围 → 设备厂商文档（p822 说明）。
